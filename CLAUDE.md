# bball-analysis

NBA analytics. Sister repo to `../bballagg`, which scrapes stats.nba.com and owns the database. This repo only **reads** that data and never writes to it. Public repo: no secrets, no data.

## Data

- **Source of truth: Postgres on honeydew**, db `bballagg`, local socket, role `bball_reader` (read-only via `pg_read_all_data`, peer auth mapped from Linux user `alex`, no password). Made by `scripts/setup_db_reader.sh`. Alex browses the same db in DBeaver.
- Access in code: `from bball import db` → `db.query(sql, **params)`, `db.tables('nba_boxscore%')`, `db.columns(t)`, `db.engine()` (marimo SQL cells use it).
- Schema, table meanings and data-quality notes live in `../bballagg/CLAUDE.md` (sections "Endpoint categories", "Schema", "Data quality"). Read them before querying a table for the first time. Key facts: tables are `nba_<endpoint>_<shard>`, `_a` is usually player rows; ids are text; game universe is `master_nba_games` (2 rows per game, one per team); V3 tables use `personid`, older ones `playerid`.
- **Zero-filled rows:** before a stat was tracked the API returns all-zero rows, and they are stored. Always filter with `bball.real.where(table, alias)` before aggregating. Open bballagg issue (Known issues 8) to make them NULL; then drop the filters.
- The data changes as bballagg scrapes. Record the date you ran an analysis in its README `data:` line.
- Never commit data. `extracts/` and `models/` are gitignored in every analysis folder.

## Layout

```
analyses/<topic>-<slug>/          one analysis (topic from topics.txt)
    README.md                     front matter: title, question, status, created, tags, parent, data
    notebook.py                   marimo
    figures/ tables/ docs/        committed (keep tables small)
    extracts/ models/             gitignored
    ideas/<slug>/                 same shape; ONE level only
src/bball/                        shared code: db, real (zero-row filters), style (plots, save helpers)
templates/analysis/               copied by `pixi run new`
tools/                            new_analysis.py, build_index.py
INDEX.md                          GENERATED by `pixi run index`; never hand-edit
IDEAS.md                          backlog of ideas not started
topics.txt                        allowed topic prefixes
```

Rules:
- Ideas nest one level only. An idea that branches off another idea is a sibling folder with `parent: <idea-slug>` in its README. An idea that grows large is promoted to its own analysis (`git mv`, set `parent:` to where it came from).
- Names: lowercase-hyphen slugs, no dates or numbers. Dates and tags go in front matter.
- New topics are added to `topics.txt` deliberately, not per analysis.
- Shared logic goes in `src/bball/` as soon as a second notebook needs it. Don't copy helpers between notebooks.
- After changing any README front matter, run `pixi run index` and commit INDEX.md with it.
- Unstarted ideas go in IDEAS.md; create a folder only when work begins.

## Commands

- `pixi run new <topic> <slug>`: new analysis. `pixi run new <analysis-folder> --idea <slug> [--parent <idea>]`: new idea.
- `pixi run edit analyses/<folder>/notebook.py`: open in marimo.
- `pixi run index`: rebuild INDEX.md.
- Lint: `uvx ruff check .` / `uvx ruff format .`.

## Environment

- pixi, conda-forge. `bball` is installed editable from `src/` (pypi-dependencies), so edits are picked up without reinstalling (restart the marimo kernel).
- pandas 3 here (bballagg pins <3 for its own reasons; doesn't apply to reading).
- GPU work: when the first model comes up, add a separate pixi feature/environment with CUDA PyTorch from conda-forge so plain analyses stay light.
